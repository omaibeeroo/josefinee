# Hanadi Store — Audit Release Gate

**Scope:** reliability, monitoring, and operational release readiness for the 21 October 2026 full-site audit.

**How to use:** Complete this gate against the exact commit being released. An unchecked item is **not passed**. Attach a CI URL, command log, dashboard screenshot, ticket, or signed owner record in the evidence column. Do not paste secret values, customer data, tokens, or personally identifiable information into evidence.

**Release decision:** Do not accept broad production traffic until all **P1 gates** and the required project checks are green, and the owner-only gates have named owners and evidence. This checklist is a control record, not proof that production is secure, legally compliant, or operationally healthy.

## Repository evidence and bounded commands

The repository currently provides these controls (their presence is not a pass for production):

- `npm run typecheck`, `npm run lint`, `npm run test`, and `npm run build` are package scripts.
- CI (`.github/workflows/ci.yml`) installs dev dependencies, applies migrations, seeds CI fixtures, runs typecheck/lint/tests, audits all installed dependencies at the configured threshold, generates a CycloneDX SBOM, builds the standalone app, and runs HTTP smoke checks.
- `npm run smoke:production` (`scripts/smoke-production.sh`) checks admin login (`200`), unauthenticated admin redirect (`307`), product `200/404`, unauthorized retention (`401`), and authorized retention (`200`) only in CI, on an HTTP loopback server with an explicitly supplied test-only secret; it refuses non-CI and non-loopback runs. CI connects the app to its disposable PostgreSQL service.
- `scripts/smoke-production-deployment.sh` checks admin login/redirect, the deployed storefront or intentional maintenance response, product behavior, unauthorized retention, and security headers; it verifies the checked-out deployment SHA, allowlists Hanadi Vercel hosts, and never sends an authorized retention request.
- `.github/workflows/production-smoke.yml` checks out the exact deployment SHA and invokes the non-mutating, host-restricted deployment smoke after a successful Production deployment; it receives no retention secret.
- `.github/workflows/staging-readiness.yml` maps Vercel's `Preview` label to the exact current `staging` ref, runs the same read-only smoke, and publishes `Staging readiness` against the tested commit SHA. `.github/workflows/promote-staging.yml` additionally requires exact-SHA CI, the latest successful Preview/readiness results, and protected review; these controls are not evidence that a staging run has passed.
- **Preview data isolation is not established (observed 2026-10-24):** the Vercel `DATABASE_URL` environment-variable record targets both Preview and Production, no staging-branch override was returned, and storage settings also target both environments. The GitHub `Preview` environment has no protection rules. Runtime Preview requests now fail closed with `503` unless Vercel's `HANADI_PREVIEW_DATA_ISOLATION_CONFIRMED=true`; readiness and promotion additionally require the matching GitHub repository variable. Set either only after an owner provisions and verifies separate Preview database and storage resources. No secret values are recorded here.
- `npm run validate:migrations` is a repository-only migration safety gate; `docs/OPERATIONS_RELEASE_RUNBOOK.md` defines the required staging rehearsal and provider-owner evidence.
- `npm run db:deploy` runs the online-index helper before `prisma migrate deploy`; migration compatibility and rollback still require release rehearsal.
- The production provider's pre-deploy migration ordering is not wired or verified by this checkout; this remains a release blocker until the owner records and tests the exact provider path.
- The maintenance contract used by deployment smoke is an intentional `503` with `X-Hanadi-Maintenance: coming-soon`. `PUBLIC_SITE_MAINTENANCE=true` may defer incomplete notification-provider configuration or an inert `console` placeholder to the owner gate to keep admin available, but sends fail closed without console delivery; this is not a provider-readiness pass. Unknown providers remain invalid, and `console` is rejected when maintenance is off.

Run only in the isolated CI environment with test fixtures. The authorized retention smoke is destructive and is allowed only against the disposable CI database enforced by the CI and loopback checks. Never run it against local, shared staging, or production data, and never print secrets.

## 3. Observability acceptance record

Before release, attach links or IDs for:

- CI run for the exact SHA, including test/build/smoke logs and SBOM.
- Staging concurrency, failure-recovery, rate-limit, admin-lifecycle, and migration rehearsal results.
- Production deployment smoke run and sanitized environment review.
- Backup restore and rollback rehearsal records with RPO/RTO.
- Monitoring dashboard and test-alert evidence, including backlog age for outbox/jobs.
- Named on-call/release/security contacts and incident runbook.
- Privacy/legal owner signoff and real-device/browser smoke notes.

## 4. Explicit non-claims

A green local build, a successful deployment, or a passing smoke script does **not** by itself prove secret entropy, cloud permissions, provider delivery, distributed enforcement, backup recoverability, rollback safety, alert coverage, on-call readiness, legal compliance, accessibility, performance, or real-device correctness. Do not mark those gates complete without the corresponding external evidence.
