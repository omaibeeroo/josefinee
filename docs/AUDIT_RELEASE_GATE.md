# Hanadi Store — Audit Release Gate

**Scope:** reliability, monitoring, and operational release readiness for the 21 October 2026 full-site audit.

**How to use:** Complete this gate against the exact commit being released. An unchecked item is **not passed**. Attach a CI URL, command log, dashboard screenshot, ticket, or signed owner record in the evidence column. Do not paste secret values, customer data, tokens, or personally identifiable information into evidence.

**Release decision:** Do not accept broad production traffic until all **P1 gates** and the required project checks are green, and the owner-only gates have named owners and evidence. This checklist is a control record, not proof that production is secure, legally compliant, or operationally healthy.

## Repository evidence and bounded commands

The repository currently provides these controls (their presence is not a pass for production):

- `npm run typecheck`, `npm run lint`, `npm run test`, and `npm run build` are package scripts.
- CI (`.github/workflows/ci.yml`) installs dev dependencies, applies migrations, seeds CI fixtures, runs typecheck/lint/tests, audits all installed dependencies at the configured threshold, generates a CycloneDX SBOM, builds the standalone app, and runs HTTP smoke checks.
- `npm run smoke:production` (`scripts/smoke-production.sh`) checks a ready storefront, a known product (`200`), an unknown product (`404`), unauthorized retention (`401`), and authorized retention (`200`) when the job secret is supplied.
- `scripts/smoke-production-deployment.sh` checks a deployed storefront or intentional maintenance response, product `200`/`404` behavior, unauthorized retention, and baseline security headers; it checks the authorized retention route only when the secret is present.
- `.github/workflows/production-smoke.yml` invokes the deployment smoke script after a successful Production deployment.
- `npm run db:deploy` runs the online-index helper before `prisma migrate deploy`; migration compatibility and rollback still require release rehearsal.
- The maintenance contract used by deployment smoke is an intentional `503` with `X-Hanadi-Maintenance: coming-soon`; outage and maintenance behavior must still be exercised in the target environment.

Run only in an isolated CI/staging environment with test fixtures. Never run destructive database, production-data, or secret-printing commands as part of this checklist.

## 3. Observability acceptance record

Before release, attach links or IDs for:

- CI run for the exact SHA, including test/build/smoke logs and SBOM.
- Staging concurrency, failure-recovery, rate-limit, admin-lifecycle, and migration rehearsal results.
- Production deployment smoke run and sanitized environment review.
- Backup restore and rollback rehearsal records with RPO/RTO.
- Monitoring dashboard and test-alert evidence, including backlog age for outbox/jobs.
- Named on-call/release/security contacts and incident runbook.
- Privacy/legal owner signoff and real-device/browser smoke notes.

## 4. Explicit non-claims

A green local build, a successful deployment, or a passing smoke script does **not** by itself prove secret entropy, cloud permissions, provider delivery, distributed enforcement, backup recoverability, rollback safety, alert coverage, on-call readiness, legal compliance, accessibility, performance, or real-device correctness. Do not mark those gates complete without the corresponding external evidence.
